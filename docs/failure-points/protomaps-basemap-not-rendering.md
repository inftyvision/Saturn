# Protomaps vector basemap renders flat grey

**Status:** resolved. **Reported by:** user, live in browser. **Date:** 2026-08-02.
**Root cause found:** 2026-08-02, see "Resolution" below.

## Symptom

`FleetMap` (`packages/ui/src/FleetMap.tsx`) was switched from CARTO raster
tiles to a self-hosted Protomaps PMTiles vector basemap. In the user's real
browser, the map renders as a single flat grey fill — no water, no land,
no roads, no labels — on every page that mounts it (`/map`, job detail,
`/hauler/map`, driver transit). Vehicle markers still render and position
correctly; only the basemap itself is blank.

The grey is not a mystery colour: `#34373d` is the DARK theme's
`background` layer paint colour, generated by `@protomaps/basemaps`'
`layers()` as the first (fallback) layer in the stack. Seeing exactly that
colour, uniformly, with zero variation anywhere in the viewport, means the
`background` layer is the only thing painting — every other layer (water,
earth, landcover, roads) is not.

## What was verified working (ruled out)

Each of these was tested directly, independent of the browser rendering
pipeline, so they're not guesses:

1. **The style JSON is valid.** Ran the real style object (source + all 71
   generated layers + glyphs + sprite URLs) through
   `@maplibre/maplibre-gl-style-spec`'s `validateStyleMin` — zero errors.
2. **Source-layer names match exactly.** `pmtiles.exe show --metadata` on
   `apps/ops/public/tiles/guyana.pmtiles` lists vector layers `boundaries,
   buildings, earth, landcover, landuse, places, pois, roads, water`.
   `protomapsLayers('protomaps', DARK, {lang:'en'})`'s layers reference the
   identical set of `source-layer` values. No schema/version mismatch
   between the Planetiler build (schema v4.15.1) and the installed
   `@protomaps/basemaps@5.7.2` package.
3. **The file serves correctly.** `curl -r 0-100` against
   `http://localhost:3050/tiles/guyana.pmtiles` returns `206 Partial
   Content` with correct `Content-Range`/`Accept-Ranges` headers, from both
   a freshly restarted dev server and the original one.
4. **The `pmtiles` npm library can read the file, in Node.** A standalone
   script using the `PMTiles`/`FetchSource` classes directly (bypassing
   MapLibre and `addProtocol` entirely) fetched the header
   (`minZoom:0, maxZoom:15`, correct bounds) and a real tile at z10
   (14,807 bytes) from the served URL.
5. **The full `Protocol.tile()` pathway works, including inside a real
   Chrome tab.** Loaded `pmtiles` fresh via `import('https://esm.sh/
   pmtiles@4.4.1')` in the browser's console and replicated exactly what
   MapLibre does: called `protocol.tile({url: 'pmtiles://http://
   localhost:3050/tiles/guyana.pmtiles', type: 'json'}, ...)` (the TileJSON
   resolution phase MapLibre does for a `type: 'vector'` source with a
   `url` field), got back a valid `{tiles, minzoom, maxzoom, bounds}`,
   substituted a real `{z}/{x}/{y}`, called `protocol.tile()` again, and
   got the same 14,807-byte tile back. `DecompressionStream` (needed for
   the archive's internal gzip compression) is available and worked.
   CORS is not a factor — same-origin.

Every piece of the data path — file, server, schema, the `pmtiles`
library's fetch+directory-walk+decompress logic — checks out, tested both
outside and inside a real browser, independent of MapLibre.

## What blocked further diagnosis (the actual failure point)

The assistant's own browser-automation tab (`claude-in-chrome` extension)
was used to try to inspect the live map instance (`isStyleLoaded()`,
`queryRenderedFeatures()`, network request timing, etc.) but produced
**inconsistent, untrustworthy readings** across repeated identical tests:

- `document.visibilityState` was `hidden` in that tab for the entire
  session, in every check, regardless of closing duplicate tabs, resizing
  the window, or clicking into the page (`hasFocus` could become `true`
  while `hidden` stayed `true` — the tab was never actually composited on
  screen in this sandbox).
- MapLibre GL JS v6's `Style.loadJSON()` (`maplibre-gl-dev.mjs:12844`)
  unconditionally awaits `browser.frameAsync(...)` — a
  `requestAnimationFrame`-wrapped promise — before calling `_load()`,
  which is what sets `this._loaded = true` and actually adds sources.
  Chrome can fully suspend (not just throttle) rAF callbacks for a frame
  that's never composited, which matches a tab stuck in `hidden` with no
  real screen presence.
- This produced contradictory-looking evidence across attempts: some
  screenshots showed the flat grey `background` fill (implying the style
  *had* loaded, since `background` is drawn from `_load()`'s layer stack),
  while a JS-level check moments later in the same tab reported
  `isStyleLoaded(): false` and `stylesheet: null`. The most likely
  explanation is that Chrome DevTools Protocol's screenshot capture can
  force a compositor paint independent of the page's own suspended rAF
  loop, so screenshots reflect a stale/partial paint while the JS-level
  style pipeline genuinely never finishes advancing in that tab.
- Removing the `pitch: 50` post-construction tilt, replacing the
  `bounds`-fit camera with a hardcoded `center`/`zoom`, and other
  isolation attempts made no observable difference — consistent with the
  rendering pipeline being blocked at a level none of those changes touch.

**Net effect:** nothing observed inside that automated tab (screenshots,
`isStyleLoaded()`, `queryRenderedFeatures()`, or request counts collected
across multiple same-domain navigations, which do not reset the
extension's request log and so accumulate noise from the assistant's own
diagnostic `fetch()` calls run in the same tab) can be trusted as evidence
about what a real, focused user browser does. Every conclusion drawn from
that tab during this investigation should be treated as unreliable.

**Confirmed conclusively:** after navigating and waiting 30+ real seconds,
reading the actual WebGL canvas's pixel data directly (`drawImage` onto a
2D canvas, then `getImageData`, sampling 12 points across the canvas) came
back `rgba(0,0,0,0)` — fully transparent — at every sample. The canvas has
never been painted a single pixel in that tab, ever, no matter how long the
wait. This means the flat-grey **screenshots** captured earlier in this
investigation were not showing real page content at all — they were some
other compositor-level artifact of the screenshot mechanism (possibly a
stale frame, or a fallback fill), because the canvas itself proves nothing
has rendered. **Every screenshot from the assistant's sandboxed tab during
this investigation should be disregarded as evidence of what the app
actually does.** The "grey" symptom is only confirmed real via the user's
own report from their real browser — not via anything the assistant
observed directly.

## Resolution

The unresolved link was exactly the one flagged above: how the fetched
vector tile data gets handed to MapLibre's parsing **worker**. It never
gets there — for two separate, stacked Turbopack bugs, not one. A first
fix (below) made the worker load the *correct* file and still didn't fix
the map; a second bug in that correct file is what actually blocked it.

### Bug 1 — MapLibre asks for the wrong worker file

`maplibre-gl` locates its own tile-parsing Web Worker script by computing
`new URL(`./${workerName}`, import.meta.url)`, where `workerName` is
chosen at runtime by a ternary between the dev and prod worker filenames.
Turbopack's `new URL(x, import.meta.url)` → static-asset rewrite only
works when `x` is a literal string; with a runtime ternary it can't decide
which of the two to bind, and instead of erroring it silently rewrites the
whole expression to the URL of **maplibre-gl's own main module** — proven
by pulling the actual chunk Turbopack served
(`0fxr_maplibre-gl_dist_maplibre-gl_mjs_0qpxa_1._.js`) and finding
`defaultWorkerUrl()` compiled down to a reference to `maplibre-gl-dev.mjs`
itself, not to either worker file.

Fixing this in isolation (`setWorkerUrl()` with a literal path, which
Turbopack *can* resolve) got the worker loading the *correct* script —
confirmed via the network log, which now showed a request to
`maplibre-gl-worker.<hash>.mjs` where before there'd been none. The map
was **still** flat grey afterwards, now with the on-map banner (see below)
reporting "tiles have not finished loading". One bug down, one to go.

### Bug 2 — even the correct worker file 404s its own dependency

Turbopack *did* build the real worker file correctly as a separate hashed
static asset (`apps/ops/.next/dev/static/media/maplibre-gl-worker.<hash>.mjs`,
confirmed serving `200` directly) — but that build step is a raw byte
copy, not a real bundle: it does **not** rewrite the worker script's own
`import … from "./maplibre-gl-shared.mjs"` to the *different* hashed
filename Turbopack gave that sibling dependency
(`maplibre-gl-shared.<other-hash>.mjs`). The literal, unhashed
`./maplibre-gl-shared.mjs` the worker asks for 404s — confirmed directly:
`curl` against that exact path returns `404`, while the actual (differently
hashed) file sits right next to it on disk. A module worker whose static
import 404s never executes a single line — not even its own
`self.worker = new Worker(...)` setup — and does so with **no console
error and no thrown exception** visible anywhere on the main thread.

Confirmed on a live map instance (temporary `window.__debugMap`):
`m.style.dispatcher.actors[0].resolveRejects` had **65 entries** — 65
messages posted to the worker, all still pending, none ever answered.
`guyana.pmtiles` got exactly one request (the TileJSON/header fetch,
which happens on the main thread, not in the worker) and then *zero*
further tile requests, ever — because the worker that's supposed to ask
for them never came alive to do so.

### The full fix

Serving MapLibre's worker as a Turbopack-processed asset doesn't work at
all for this file, in either form — not the library's own lookup, not
Turbopack's own correctly-hashed copy. Both routes go through the same
broken "copy `.mjs` without rewriting its sibling import" pipeline. The
fix sidesteps that pipeline entirely, the same way `guyana.pmtiles`
already does: vendor a plain, unhashed copy of both files together into
`public/` (`apps/ops/public/` and `apps/buyer/public/` — both apps mount
`FleetMap`), so the relative import between them resolves exactly as it
does in the installed package, with Turbopack never touching either file:

```ts
import { setWorkerUrl } from 'maplibre-gl';
setWorkerUrl(new URL('/maplibre-gl-worker.mjs', window.location.origin).href);
```

Called once, guarded the same way as `ensurePmtilesProtocol`, before the
first `Map` is constructed.

**Verified** on a clean `location.reload()` of `/map`: 10 real tile
requests to `guyana.pmtiles`, all `206`; the on-map error banner is gone;
water, coastline, roads and place labels (Anna Regina, Suddie, Timehri,
Mahaica) render under the fleet markers instead of flat grey.

## Note on the on-map error banner

`FleetMap` grew a visible error banner during this investigation (an
`m.on('error', ...)` handler plus an 8s `isSourceLoaded` timeout) so a
real user's browser could self-report a failure the assistant's
automation tooling couldn't reliably observe. It's still in the shipped
file — and it was, in the end, exactly what let the user catch that the
first fix alone hadn't actually resolved this. Worth keeping.
